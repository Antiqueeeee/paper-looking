# 个人论文库系统 BDD 规格说明

- 文档版本：v0.1（MVP 范围）
- 状态：待评审
- 目标部署：单台 VPS，2C4G / 20GB 磁盘
- 核心技术约定：
  - 元数据索引：SQLite（WAL）
  - PDF 解析：MinerU API
  - 翻译与问答：OpenAI 兼容 LLM API
  - 全库问答检索：DCI（Direct Corpus Interaction），使用 `rg` / `grep` / `sed` / `sqlite3` 等只读终端工具，不引入向量数据库
  - PDF 冷存储：COS / OSS / S3 兼容对象存储
  - 定时任务：APScheduler / cron + 单 worker 进程
- 访问入口：Tailscale / Cloudflare Tunnel / 安全组白名单，不直接暴露公网

---

## 1. 背景、角色与术语

### 1.1 用户画像

| 角色 | 说明 |
|---|---|
| 论文库所有者（用户） | 唯一直接使用者。每天接收早报、勾选论文、阅读和提问，偶尔手动上传 PDF |
| 系统（worker） | 定时抓取、翻译、调用 MinerU、执行磁盘策略、发送提醒 |
| AI 问答 Agent | 在论文语料目录内使用只读命令检索证据并生成带引用的回答 |

### 1.2 用户目标

1. 每天自动获取关注领域的新论文，并获得中文摘要式早报。
2. 看到感兴趣的论文时，只做一次“勾选”，系统自动完成 PDF 获取、解析、翻译和入库。
3. 阅读论文时可以对照中文翻译，并随时向 AI 提问。
4. 可以针对整个论文库做深度提问，回答必须可追溯到原文。
5. 系统部署在低配云服务器上，日常维护成本接近零。

### 1.3 术语

| 术语 | 含义 |
|---|---|
| 论文记录 | SQLite `papers` 表中的一条元数据，主键为 ACL ID 或 DOI |
| 兴趣标签 | `kg / ie / kbqa / sp / ds / rag / mrag / mem` 等标签，由关键词规则匹配产生 |
| 阅读队列 | 用户在早报中勾选、准备深读的论文集合 |
| 双语全文 | 英文原文 Markdown + 中文翻译 Markdown，成对保存 |
| 缺 PDF | 没有开放下载、需要用户手动上传 PDF 的论文状态 |
| DCI 语料目录 | 存储论文 Markdown 的本地目录，AI 问答时使用 `rg` 等命令直接搜索 |

### 1.4 优先级约定

| 优先级 | 含义 |
|---|---|
| P0 | MVP 必须实现，否则日常主线无法跑通 |
| P1 | MVP 内应实现，影响体验或数据可靠性 |
| P2 | 可在 MVP 之后补，不影响主流程 |

### 1.5 验收条件约定

- 每个场景由 Gherkin 的 Given / When / Then 描述行为。
- 每条场景下的“验收条件”是提交测试和验收时必须逐条通过的量化标准。
- 标注“可配置”的阈值允许通过配置文件修改，但必须有默认值。
- 验收测试的测试数据至少包含：
  - 100 篇合成论文元数据；
  - 20 个真实 Markdown 全文样本；
  - 5 个含公式、表格、双栏内容的 PDF 样本；
  - 1 个损坏 PDF、1 个超大 PDF（>100MB）。

## 2. 功能场景

## FEAT-00 端到端用户旅程

### 场景 0.1 标准的一天

```gherkin
Given 系统已部署并完成初始化
And 定时抓取任务配置为每天 07:30 运行
When 新的一天开始
Then 07:30 系统自动完成多源增量抓取、去重、兴趣匹配和标题摘要翻译
And 08:00 前生成当日中文早报
And 用户在早报中勾选 0 到 N 篇论文
And 被勾选论文自动进入 PDF 获取 → MinerU 解析 → 全文翻译流水线
And 用户当天可打开任意已解析论文进行双语阅读和单篇问答
And 用户可随时针对全库提问并获得带原文引用的回答
```

验收条件：
- P0：从定时抓取到早报可见，全程无需用户操作。
- P0：用户在早报中的勾选操作是唯一必须的人工动作；不勾选也不影响其他功能。
- P0：当用户不勾选任何论文时，系统不产生解析和全文翻译费用。
- P0：流程中任一环节失败，均可在详情页看到状态和重试入口。
- P1：用户可在手机上完成看早报、勾选和提问三个动作。

### 场景 0.2 一篇外部 PDF 的入库旅程

```gherkin
Given 用户从导师、网页或其他渠道获得一篇论文 PDF
When 用户将 PDF 拖入上传入口
Then 系统校验文件并匹配或创建论文记录
And 自动触发 MinerU 解析
And 解析成功后自动触发全文翻译
And 完成后该论文出现在论文库中，可阅读、可提问
```

验收条件：
- P0：从上传完成到论文出现在库中，状态全程可追踪。
- P0：上传后无需用户手工建目录、重命名、转 Markdown。
- P0：若元数据无法自动匹配，系统提示用户补充标题/年份/标签，但 PDF 和解析结果不丢失。
- P1：整个流程在测试 PDF（约 1MB）上默认 ≤ 10 分钟完成解析，翻译时间取决于 API 队列。

## FEAT-01 数据采集与定时更新

### 场景 1.1 首次导入现有采集数据

```gherkin
Given 项目目录中存在历史采集的 JSONL 文件（ACL 2024-2026、期刊 2025-2026）
When 用户运行初始化命令，例如 paper init
Then 系统读取所有 JSONL 并按主键（ACL ID / DOI）导入 SQLite
And 同一主键的重复记录只保留一条，且保留最完整的摘要和标签
And 导入完成后生成导入报告，显示来源、总数、去重数和失败数
```

验收条件：
- P0：10 万条以内元数据导入时间 ≤ 5 分钟（2C4G）。
- P0：重复主键去重后，数据条数等于唯一主键数。
- P0：导入失败的行写入 `import_errors.log`，不影响其他行导入。
- P0：导入是可重复执行的；第二次导入不会产生重复数据。
- P1：旧数据中的 `id / title / authors / abstract / year / venue / url / pdf_url / tags` 字段全部进入 `papers` 表。

### 场景 1.2 每日定时增量抓取

```gherkin
Given 系统已初始化，且抓取源配置为 ACL Anthology、OpenAlex（期刊）和 arXiv（可选）
And 定时任务配置为每天 07:30 触发
When 到达触发时间
Then 系统依次执行三个数据源的增量抓取
And 新抓取到的记录按主键 upsert 到 SQLite
And 已存在的记录更新摘要、PDF 链接和可获取字段，不覆盖用户笔记
And 每次抓取后记录 source、last_run、新增数、失败数
```

验收条件：
- P0：定时任务按配置时间自动运行，无需人工操作。
- P0：同一数据源同一天重复运行不会产生重复论文记录。
- P0：ACL 抓取复用已有 `.done` / checkpoint 机制，中断后可续跑。
- P0：OpenAlex 使用增量时间窗口（例如 `from_publication_date`），不重复拉全量。
- P1：用户可通过 CLI 手动触发抓取：`paper fetch --source acl`。
- P1：抓取成功/失败结果写入日志，保留最近 30 天。

### 场景 1.3 抓取失败重试与告警

```gherkin
Given 某个数据源在抓取过程中超时或返回错误
When 单次请求失败
Then 系统自动按退避策略重试，默认重试 3 次
And 超过重试次数后将该任务标记为 failed
And 系统在下次定时运行前发送一条失败提醒
And 已成功抓取的部分数据仍然保存，不整体回滚
```

验收条件：
- P0：失败任务不会阻塞其他数据源或其他论文的抓取。
- P0：重试后的失败原因和 URL 记录在日志中。
- P1：连续 3 次抓取失败时，提醒升级为高优先级通知。

### 场景 1.4 元数据完整性约束

```gherkin
Given 抓取到的论文记录
When 记录被写入数据库
Then title 和主键不得为空
And 年份必须合法，来源必须属于已配置来源集合
And URL 和 PDF URL 若存在必须是 http/https 格式
```

验收条件：
- P0：缺失 title 或主键的记录被拒绝入库并记录原因。
- P0：空摘要允许入库，`abstract` 为空字符串，不影响后续筛选和翻译。
- P1：无 `pdf_url` 的期刊论文默认标记为“缺 PDF”。

## FEAT-02 兴趣筛选与每日早报

### 场景 2.1 新论文自动匹配兴趣标签

```gherkin
Given 有新增论文记录，且系统中配置了关键词规则组
When 增量抓取完成后
Then 系统对每篇新论文的 title + abstract 运行规则匹配
And 命中论文获得一个或多个兴趣标签
And 未命中论文仍保存到全量库，但不进入早报
```

验收条件：
- P0：标签规则与现有 `filter_papers.py` 的 `KEYWORD_GROUPS` 语义一致。
- P0：规则匹配大小写不敏感，支持正则。
- P0：标签结果写入 `papers.tags`，可被筛选和统计。
- P1：规则文件可配置、可热更新；用户修改规则后可对指定日期范围重跑匹配。
- P1：重跑规则不会覆盖用户手工添加或移除的标签。

### 场景 2.2 标题与摘要翻译

```gherkin
Given 一批新论文已匹配兴趣标签
When 翻译任务开始
Then 系统调用 OpenAI 兼容 LLM API 翻译 title 和 abstract
And 翻译结果保存到 `title_zh` 与 `abstract_zh`
And 每篇论文只翻译一次；重跑时优先使用缓存
And 翻译失败记录在任务表中并自动重试一次
```

验收条件：
- P0：翻译结果按 `(paper_id, text_hash)` 缓存；相同内容不重复计费。
- P0：原文变化时重新翻译；原文未变化时不重新翻译。
- P0：单篇翻译失败不影响其他论文。
- P1：单批翻译默认并发 ≤ 5，避免触发限流。
- P1：翻译任务有每日预算上限，超限自动暂停并通知。

### 场景 2.3 生成每日早报

```gherkin
Given 今日新增论文已完成标签匹配和标题摘要翻译
When 早报生成任务执行
Then 系统按兴趣标签分组生成中文 Markdown 摘要
And 每组按年份/来源/相关度排序
And 早报显示每篇论文的标题、中文标题、摘要、来源和 PDF 状态
And 早报包含“今日新增总数”和“兴趣命中数”统计
```

验收条件：
- P0：早报在每日 08:00 前生成完毕（默认配置）。
- P0：当天无新增兴趣论文时，早报明确显示“今日无新增相关论文”。
- P0：早报中每篇论文都可点击进入论文详情页或阅读器。
- P1：早报支持按标签查看，一篇多标签论文在主要分组中展示并在次要分组中交叉引用。
- P1：早报保留历史归档，可按日期回看。

### 场景 2.4 阅读队列勾选

```gherkin
Given 用户正在查看某天的早报
When 用户勾选一篇或多篇论文
Then 这些论文状态从 new 更新为 in_queue
And 系统自动创建后续任务：开放 PDF 下载、MinerU 解析、全文翻译
And 未开放 PDF 的论文进入“待上传”列表
```

验收条件：
- P0：勾选操作即时生效，响应时间 ≤ 1 秒。
- P0：同一篇论文重复勾选不会创建重复任务。
- P0：任务创建幂等：以 `(paper_id, task_type, content_hash)` 唯一。
- P1：用户可批量勾选并一键取消。

## FEAT-03 PDF 获取与手动上传

### 场景 3.1 开放 PDF 自动下载

```gherkin
Given 一篇阅读队列中的论文有开放 PDF 链接
When 下载任务执行
Then 系统下载 PDF 到本地 PDF 目录，文件名为 paper_id.pdf
And 数据库记录 local_pdf 路径和下载时间
And 论文的 PDF 状态更新为 downloaded
```

验收条件：
- P0：下载失败自动重试 2 次，仍失败则保持“缺 PDF”并记录原因。
- P0：下载文件校验：文件大小 > 0，且 MIME 或文件头为 PDF。
- P0：同一篇论文不重复下载已存在的有效 PDF。
- P1：请求带 User-Agent，并遵守服务器响应中的限速提示。
- P1：单文件下载超时默认 120 秒。

### 场景 3.2 未开放 PDF 标记为待上传

```gherkin
Given 一篇阅读队列中的论文没有开放 PDF 链接
When 用户勾选该论文
Then 系统将其 PDF 状态标记为 needs_upload
And 该论文出现在“待上传”列表中
And 其元数据、原文链接和 DOI 在详情页可用
```

验收条件：
- P0：待上传列表可筛选、按勾选时间排序。
- P0：系统不尝试从需要订阅或授权的页面抓取 PDF。
- P1：用户上传完成后，对应记录自动移出“待上传”列表。

### 场景 3.3 手动上传 PDF

```gherkin
Given 用户有一个本地 PDF 文件
When 用户通过 Web 上传入口或 CLI 将 PDF 提交给系统
Then 系统校验文件类型和大小
And 若用户未指定论文记录，则系统提取元数据并尝试与现有记录按标题/DOI 匹配
And 匹配成功则关联到已有论文记录，否则创建一条 source=manual 的新记录
And 上传完成后自动创建 MinerU 解析任务
```

验收条件：
- P0：接受 PDF；非 PDF 文件被拒绝并提示。
- P0：默认单文件上限 100MB，超过则拒绝，阈值可配置。
- P0：上传成功后原始 PDF 保存到 `pdf/` 目录，命名与 paper_id 对应。
- P0：按标题/DOI 匹配失败的 PDF 不会静默丢弃，而是创建手动记录并提示用户补充元数据。
- P1：Web 上传支持拖拽和多文件。

### 场景 3.4 重复上传去重

```gherkin
Given 用户上传一个系统已存在的 PDF
When 系统计算文件 SHA-256
Then 若与已有 PDF 哈希相同，则不重复保存文件
And 系统提示“已存在”，并跳转到已有论文详情页
```

验收条件：
- P0：重复上传不会创建第二条论文记录。
- P0：重复上传不会覆盖用户已有笔记和标签。
- P1：若同名但内容不同的 PDF，作为新版本保存，旧版本保留并可回溯。

## FEAT-04 MinerU PDF 解析

### 场景 4.1 阅读队列自动触发解析

```gherkin
Given 论文进入阅读队列且 PDF 已就绪
When worker 调度到该论文
Then 系统提交 MinerU API 解析任务
And 记录任务状态 queued → uploading → parsing → downloading
And 解析完成后保存 Markdown 到 DCI 语料目录
```

验收条件：
- P0：MinerU 使用 API，不在服务器本地加载模型。
- P0：任务状态可在数据库 `tasks` 表中查询。
- P0：单 worker 默认同时处理 ≤ 2 个 MinerU 任务。
- P1：任务优先级：阅读队列新任务优先于批量重试任务。

### 场景 4.2 解析任务幂等与断点恢复

```gherkin
Given 一个 MinerU 任务曾因进程重启而中断
When worker 重新启动
Then 系统能根据任务状态恢复或重新提交任务
And 不会产生重复的解析结果文件
```

验收条件：
- P0：`tasks` 表以 `(paper_id, task_type, content_hash)` 唯一约束。
- P0：进程重启后，queued 和 uploading 状态任务可安全重试。
- P0：已完成任务在重启后不会再次调用 MinerU API。
- P1：调用 MinerU 前先检查目标 Markdown 是否已存在且有效。

### 场景 4.3 解析结果校验与失败处理

```gherkin
Given MinerU 返回了解析结果
When 系统下载 Markdown 文件
Then 系统校验文件非空、可解码为 UTF-8、正文字符数 ≥ 200（默认）
And 校验失败时自动重试一次
And 两次失败后论文标记为 parse_failed，并在详情页展示原因
```

验收条件：
- P0：空文件、纯图片 Markdown、不可解码文件视为解析失败。
- P0：parse_failed 论文保留 PDF 和错误信息，允许用户手动重新触发。
- P1：失败原因至少记录：API 状态码、重试次数、结果文件大小和校验结果。
- P1：连续失败超过 5 篇时暂停该解析任务队列并告警，防止 API 配置错误导致持续计费。

### 场景 4.4 解析产物规范

```gherkin
Given 一篇论文解析成功
When Markdown 写入语料目录
Then 文件路径遵循 {source}/{year}/{venue}/{paper_id}.md
And 文件头部写入 front-matter：id、title、authors、year、venue、source、tags、pdf_url
And 正文为 MinerU 原始输出，不做额外清洗
```

验收条件：
- P0：paper_id 在文件路径中唯一且可反查数据库。
- P0：front-matter 为合法 YAML，可被 Python 标准库加 PyYAML 解析。
- P0：正文与 MinerU 输出一致，不截断、不重排。
- P1：同一论文重新解析时写临时文件，成功后再原子替换，避免半成品。

## FEAT-05 全文翻译

### 场景 5.1 阅读队列论文自动全文翻译

```gherkin
Given 一篇论文已生成英文 Markdown 全文
When 全文翻译任务执行
Then 系统按章节或固定长度块调用 LLM API 翻译
And 中文结果保存为 {paper_id}.zh.md
And 章节标题、Markdown 结构、表格和 LaTeX 公式尽量保留
And 翻译完成后论文状态更新为 translated
```

验收条件：
- P0：英文 Markdown 在翻译过程中不被修改。
- P0：翻译结果与原文文件成对存在，命名规则固定。
- P0：单篇翻译失败自动重试一次；仍失败则标记 translation_failed。
- P1：长文按 4000–8000 字符分块，块间不丢失 Markdown 边界。
- P1：术语保留策略可配置，默认保留 GraphRAG、KBQA、entity alignment 等英文术语。

### 场景 5.2 翻译缓存与幂等

```gherkin
Given 一篇论文已经翻译过
When 系统因重复勾选、重跑或恢复任务再次处理该论文
Then 若原文哈希未变化，系统直接使用已有翻译，不重新调用 API
And 若原文重新解析导致哈希变化，则重新翻译并覆盖旧中文文件
```

验收条件：
- P0：翻译任务键为 `(paper_id, source_md_sha256)`。
- P0：重复触发不会产生重复 API 调用和重复中文文件。
- P1：可统计每篇论文的翻译 API 调用次数和累计 token 消耗。

### 场景 5.3 翻译预算控制

```gherkin
Given 系统配置了每日翻译预算上限
When 当日累计翻译 token 达到预算的 100%
Then 系统暂停创建新的全文翻译任务
And 已入队的任务保留，次日按优先级继续
And 用户收到预算提醒
```

验收条件：
- P0：默认预算可配置，超限自动熔断。
- P0：熔断后早报、抓取、问答等非翻译功能不受影响。
- P1：预算使用情况可在设置页查看（今日、本月）。

- P1：支持多标签“任一命中”和“全部命中”两种模式。

### 场景 6.2 阅读状态管理

```gherkin
Given 一篇论文处于阅读队列中
```

- P1：done 和 later 论文默认不进入每日早报，但仍在全库可搜。

### 场景 6.3 标签与笔记

验收条件：

- P1：笔记支持 Markdown，单条长度 ≥ 1 万字符不报错。
- P1：笔记可导出为该论文单独的 Markdown 文件。

### 场景 6.4 库统计

```gherkin
And 显示阅读队列、已读、缺 PDF、解析失败的数量
```

- P0：统计数字与数据库实际计数一致。
- P1：支持按时间范围查看增长趋势。

## FEAT-08 DCI 全库 AI 问答

### 场景 8.1 单篇论文问答

```gherkin
Given 用户打开一篇已解析论文
When 用户提问：“这篇论文的核心方法是什么？”
Then AI Agent 只在该论文对应的 Markdown 文件内使用只读命令检索
And 回答必须引用文件路径和行号，例如 [md/2026.findings-acl.38.md:210]
And 回答按 Explanation / Exact Answer / Confidence 格式输出
```

验收条件：
- P0：单篇问答不访问其他论文文件，不访问外网。
- P0：回答中至少 1 条引用，且引用内容可在原文中找到。
- P0：若问题超出该论文范围，Agent 明确说明“未在本文中找到证据”。
- P1：单篇问答默认 40 秒内开始输出答案。

### 场景 8.2 全库深度问答（元数据预筛选 + grep）

```gherkin
Given 用户在全库问答框提问：“2026 年 findings 里 GraphRAG 论文在检索机制上有哪些共同趋势？”
When 用户提交问题
Then 系统先用 SQLite 元数据条件（年份、来源、标签等）缩小候选论文范围
And Agent 在候选论文的 Markdown 文件中使用 rg/grep 搜索、读取局部上下文并交叉验证
And Agent 归纳回答，并列出每篇被引用的论文及其行号
```

验收条件：
- P0：候选范围通过 SQLite 筛选，而非遍历全库文件名。
- P0：rg 搜索只发生在 DCI 语料目录，不能访问系统其他目录。
- P0：回答中每篇论文至少 1 条可验证引用；无法验证的引用不得出现。
- P0：当没有足够证据时，Agent 输出“未找到足够证据”，Confidence < 50%。
- P1：1 万篇 Markdown 规模下，单次全库问答默认 ≤ 30 次工具调用。
- P1：回答附带的论文列表可点击进入阅读器。

### 场景 8.3 精确术语检索

```gherkin
Given 用户问：“我库里哪些论文使用了 OpenAlex 的 abstract_inverted_index？”
When Agent 执行搜索
Then Agent 使用 rg 正则匹配该精确术语及其常见变体
And 返回命中论文列表和命中片段
```

验收条件：
- P0：对语料中确实存在的精确术语，召回率 100%（在 20 个真实全文测试样本上验证）。
- P0：每个命中结果都有文件路径和行号。
- P1：Agent 能自动扩展同义表达，例如 inverted abstract / abstract reconstruction。

### 场景 8.4 无证据诚实回答

```gherkin
Given 用户提出一个论文库中没有答案的问题
When Agent 完成搜索后没有找到可靠证据
Then Agent 不编造论文和引用
And 明确回答“库中未找到相关证据”
And Confidence 低于 50%
```

验收条件：
- P0：在 10 个构造的“无证据问题”测试集上，编造引用次数 = 0。
- P0：系统不因无证据而调用外部搜索引擎。
- P1：Agent 可建议更接近库内主题的提问方式。

### 场景 8.5 论文对比问答

```gherkin
Given 用户指定两篇论文 A 和 B，并提问：“A 和 B 的方法有什么区别？”
When Agent 执行任务
Then Agent 分别在 A、B 文件内检索方法章节和实验设置
And 输出对比表或分点说明，并分别引用 A、B 的行号
```

验收条件：
- P0：每篇论文至少 1 条引用。
- P0：对比结论若某篇缺失对应信息，明确标注“B 中未提及”。
- P1：对比任务支持一次指定 2–5 篇论文。

### 场景 8.6 问答工具安全约束

```gherkin
Given AI Agent 可以调用终端工具
When Agent 执行命令
Then 系统只暴露白名单命令：rg、grep、find、ls、sed、head、sqlite3（只读模式）
And 所有命令在只读语料目录或 SQLite 只读连接上执行
And 禁止网络访问、禁止写文件、禁止执行任意 python -c / bash -c
```

验收条件：
- P0：工具执行层使用命令白名单，不在 shell 中拼接自由命令。
- P0：写操作被操作系统或执行层拦截并记录。
- P0：SQLite 打开时使用 `file:...?mode=ro` 只读 URI。
- P0：单次工具输出默认截断为 12000 字符，可配置。
- P1：Agent 无法通过路径穿越访问语料目录之外的文件。

### 场景 8.7 成本与上下文控制

```gherkin
Given 单次全库问答默认预算为 30 次工具调用
When Agent 达到工具调用上限或 token 上限
Then 系统强制要求 Agent 基于已有证据输出最终回答
And 若已有证据不足，输出“未找到足够证据”
And 本次任务的 token 消耗记录到数据库
```

验收条件：
- P0：单次问答 token 使用量可查询。
- P0：达到上限不会无限循环，必然终止。
- P1：工具输出采用 DCI 的截断/压缩策略，保留最近关键上下文。

### 场景 8.8 模型 API 不可用

```gherkin
Given 问答或翻译所使用的 LLM API 返回错误或超时
When 系统收到错误
Then 自动重试一次
And 仍失败时向用户返回“AI 服务暂时不可用”，并保留问题草稿
And 不影响论文库浏览和 rg 元数据搜索
```

验收条件：
- P0：API 故障时系统不崩溃，Web 页面正常。
- P0：失败的问题记录在 `qa_logs` 中，可一键重试。
- P1：连续故障超过 10 分钟触发告警。

## FEAT-09 存储、备份与运维


### 场景 9.2 PDF 冷热分离

```gherkin
Given 本地 PDF 目录超过配置的热存储上限
When 淘汰任务执行
Then 系统按最近访问时间 LRU 选择 PDF
And 将 PDF 上传至对象存储，校验成功后删除本地文件
And 数据库记录 object_key，状态改为 cold

```

验收条件：
- P0：只有上传校验成功后才删除本地 PDF。
- P0：手动上传且未完成 MinerU 解析的 PDF 不参与自动淘汰。
- P0：取回操作有明确进度提示，失败可重试。
- P1：对象存储上传/下载失败不影响元数据和 Markdown 可用性。

### 场景 9.3 SQLite 备份与恢复

```gherkin
Given 系统运行中
When 数据库文件发生写入
Then 备份进程持续复制 WAL 到对象存储（Litestream 或等价方案）
And 每日保留一个完整快照
```

验收条件：
- P0：恢复演练：从对象存储恢复到新目录后，数据库可正常打开。
- P0：最近一次成功复制的延迟 ≤ 1 分钟。
- P1：恢复后不丢用户标签、笔记和任务状态。

### 场景 9.4 服务健康与资源限制

```gherkin
Given 系统以两个 systemd 服务运行：paper-web 和 paper-worker
When 任一服务异常退出
Then systemd 自动重启
And 连续失败时记录错误并告警
```

验收条件：
- P0：`paper-web` 内存上限 512M，`paper-worker` 内存上限 1G。
- P0：健康检查端点返回数据库连接状态和磁盘剩余空间。
- P1：worker 单实例运行，防止调度重复。

### 场景 9.5 访问安全

```gherkin
Given 系统部署在云服务器上
When 用户从电脑或手机访问
Then 仅允许通过 Tailscale / Cloudflare Tunnel / 安全组白名单访问
And 不对公网开放 80/443/8000 端口
```

验收条件：
- P0：公网端口扫描无法直接访问 Web 服务。
- P0：未认证的局域网设备访问时，系统可配置访问令牌。
- P1：敏感配置（API Key）不写入代码库或日志。
